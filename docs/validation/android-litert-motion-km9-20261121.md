# KM9：现有 LiteRT ESRGAN ×4 能否用于播放时超分？

**不能在这台手机上用现有 CPU 实现逐帧增强 30 fps 视频。** 取[实拍盲评](android-motion-natural-km9-20261121.md)相同的三个 MP4，每段仅测第 3 秒的一帧。增强最少用 37.11 秒；实时播放每帧只有 33.33 毫秒。不把 LiteRT 加入自动播放或回退链；保留现有可选文件导出能力。没有改动播放器，也没有让参与者给预渲染视频打分。

| 场景 / 输入 | 4× 输出 | 分块数 | 整帧耗时 | 相当于多少个 30 fps 帧预算 |
|---|---|---:|---:|---:|
| 电影人物 / 640×360 | 2560×1440 | 209 | 65.88 秒 | 1976 |
| 瀑布 / 480×270 | 1920×1080 | 120 | 37.11 秒 | 1113 |
| 飞鸟 / 640×360 | 2560×1440 | 209 | 64.46 秒 | 1934 |

**测到哪一段。** 在用过上述影片的同一台 TECNO KM9（Android 15 / API 35）上，以独立前台测试 App 运行[当前模型封装](../../android/backend-litert-sr/src/main/kotlin/io/ondeviceai/litertsr/EsrganInterpreter.kt)和[分块拼接](../../android/backend-litert-sr/src/main/kotlin/io/ondeviceai/litertsr/EsrganTiles.kt)的原样副本。固定 `com.google.ai.edge.litert:litert:1.4.2`，四线程 CPU，运行日志确认 XNNPACK 接管全部 497 个节点；用项目既有 4,993,712 字节 ESRGAN 模型（SHA-256 `1a380d3744103e11ef343534aaff54815cae40769dcd00c023652a7e5bc47f4b`）。每块输入 50×50，四周各 8 像素，实际步长 34。用第一场真实素材的一块预热，耗时 505 毫秒，未计入表格。共 538 次计时分块，最快 304.35 毫秒。表中包含分块准备、推理和结果拼接，不含解码、颜色转换、PNG 读写、编码、渲染或等待上屏。它是离线测试，不是屏幕帧率统计。每场只测一帧，不推算持续播放帧率或 P95。

**同一帧的画质。** 先独立重制三个输入文件，SHA-256 均与盲评原件一致。分别取编码后的输入和裁切、帧率转换相同的原始素材第 90 帧（从 0 开始）；原始参考取自缩小和低清编码之前。对照组从解码后的同一输入做双线性 4× 放大；双线性和真机 ESRGAN 输出均用相同 Lanczos 滤镜缩回参考尺寸，再以 8 位 BT.709 亮度计算 PSNR 和 SSIM，越高越接近对应参考。这不是播放器原画路径的屏幕截图。

| 场景 | 参考尺寸 | 双线性 PSNR / SSIM | ESRGAN PSNR / SSIM |
|---|---|---:|---:|
| 电影人物 | 948×534 | 33.28 dB / 0.9401 | 33.02 dB / 0.9321 |
| 瀑布 | 480×270 | 33.08 dB / 0.9235 | 32.88 dB / 0.9293 |
| 飞鸟 | 1280×720 | 45.08 dB / 0.9905 | 43.28 dB / 0.9853 |

电影和飞鸟的两个指标均低于双线性；瀑布 SSIM 略高、PSNR 略低，且原始参考只有 480×270，不能据此判断是否恢复了额外细节。电影和飞鸟的原始色彩矩阵未指定，按前轮约定以 BT.709 解释。三张静态图不能代表连续播放时的人眼偏好、运动稳定性或所有内容的质量。

**覆盖范围。** [SDK 后端](../../android/backend-litert-sr/src/main/kotlin/io/ondeviceai/litertsr/LiteRtVideoSuperResolutionBackend.kt)以文件为输入并产出 MP4，模块声明最低 API 26；本次真机只覆盖 API 35。没有测其他模型、线程数、GPU/NPU delegate 或其他机型。若开发新的实时学习型路线，应先在这三份同源输入上过 33.33 毫秒的整帧计算筛查，再进播放器验证同帧上屏、回退、连续帧质量与音画节奏。
