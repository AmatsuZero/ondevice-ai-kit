# W6 视频问答能看到哪些时刻

2026-11-27，统一 Demo 的 WeMM 后端在 Mac 上完成两组对照。在 32 秒短片里，同一段两秒划艇镜头移过一个采样点，回答就从「没看到」变为「有，室外的人正在划皮划艇。」五分钟长片里的钓鱼镜头也出现了相同现象。下表中的时间都是相对影片起点的播放时间。[逐次原答、实际帧时间和 RGB 摘要](w6-video-temporal-coverage-20261127.json)

## 32 秒短片中的两秒划艇

三份短片使用相同的室内素材，均问「视频中有没有室外场景？如果有，用一句话说明室外的人在做什么；如果没看到，请说没看到。」后端实际读取第 0、4、8、12、16、20、24、28 秒的画面。外景取自事先标注的激流划艇视频。

| 输入 | 实际送入的划艇画面 | 回答 |
| --- | ---: | --- |
| 全程室内 | 0 帧 | 没看到。 |
| 第 9 至 11 秒划艇 | 0 帧 | 没看到。 |
| 第 7 至 9 秒划艇 | 1 帧（第 8 秒） | 有，室外的人正在划皮划艇。 |
| 从第二份短片实际截取第 9 至 11 秒，单独问「这个两秒片段里的人在做什么？」并要求只说能确认的动作 | 8 帧 | 在湍急的河流中划船，使用船桨进行划行。 |

对含划艇镜头的整片直接问「请看第9到11秒：画面里的人在做什么？只说能从画面确认的动作。」实际输入仍是原来八帧。回答开始描述衣着，在「穿着白色」处中断，没有答出划艇。另用独立的两秒原素材提原问题，也答出了划皮划艇；实际截片与这份原素材的八帧 RGB 摘要逐一相同。这组共六次调用，每种条件一次。

## 五分钟长片中的五秒钓鱼

三份长片每份 2,400 帧。模型从第 0 秒开始每隔 37.5 秒取一帧，最后一帧在 262.5 秒。四种输入沿用相同问题，轮换顺序，在同一后端连续交替 24 轮。每行的 24 次共用一份素材，用于观察重复性。

| 输入 | 实际送入的钓鱼画面 | 24 次回答 |
| --- | ---: | --- |
| 全程室内 | 0 帧 | 全部回答「没看到」 |
| 第 120 至 125 秒钓鱼 | 0 帧 | 全部回答「没看到」 |
| 第 110 至 115 秒钓鱼 | 1 帧（第 112.5 秒） | 全部回答「有，室外的人正在河边钓鱼。」 |
| 单独五秒钓鱼 | 8 帧 | 全部答出室外的人正在河边钓鱼 |

在推理前，独立解码确认两份含外景的长片确实包含同一镜头。主干的视频准备代码对前两份长片给出了逐一相同的八帧 RGB 摘要，第三份只改变了第四帧，该帧与五秒单片的中间帧一致。32 秒对照也核对了对应的八帧。整片回答「没看到」仍可能漏掉采样间隔内真实发生的动作。

## 连续调用的资源读数

Apple M5 Pro（48 GiB）使用与主干源码核对过的 WeMM 后端、固定权重和默认 32 token。96 个请求中，72 个读取五分钟视频，24 个读取五秒单片；全部返回非空答案。首个非空更新的中位耗时为 0.854 秒，完整答案为 0.972 秒，完整答案 P95 为 1.111 秒，最慢一次为 2.340 秒。每次从调用后端到返回计时，含抽帧与生成。P95 取排序后的第 92 项。

计入模型安装、96 次问答和清理，进程总用时 98.88 秒。Darwin `time -l` 记录的物理内存峰值为 401,001,376 B，最大 RSS 为 2,884,943,872 B。结果适用于这次 Mac 连续运行。iPhone 已有一次预热后短答的页面内存测量，持续问答期间的真机内存、热状态与电池耗电仍待测。[iPhone 短答测量](../../demo/iosApp/UITests/Fixtures/WeMM/README.md#测量短回答期间的-app-进程内存)

这两组使用已有素材剪成对照，102 次调用共覆盖两种户外活动。日常开放问答的质量仍按独立题集评估。[v1.1 开放问答对照](w6-video-open-qa-v1.1.md)

## 从 Demo 选片时的文件大小上限

上面的 Mac 问答直接把文件交给后端。iOS 统一 Demo 先把用户从 Files 选中的单个视频复制到临时目录，上限为 32 MiB。另在 Mac 上编译同一份 `MultimodalInputStore`，从 Demo 使用的异步导入入口传入 39 段已有视频。每个成功导入的副本均与源文件 SHA-256 一致；释放后逐项核对了临时目录。[导入实现](../../demo/iosApp/MultimodalInputStore.swift) · [宿主接入](../../demo/iosApp/MultimodalModelHostFactory.swift)

| 素材 | 导入成功 | 超过上限 |
| --- | ---: | ---: |
| 开放问答 v1.1 的 12 段原片 | 12 | 0 |
| 上述三份五分钟长片 | 3 | 0 |
| 旧 Qwen2-VL 试验的 24 段原片 | 20 | 4 |

四段超限原片时长仅 31.765–35.016 秒，大小为 34,579,266–91,078,692 字节。另给同一段色序影片添加 MP4 `free` 数据块，三份影片解码后的画面摘要相同。33,554,431 和 33,554,432 字节的两份可导入，33,554,433 字节的一份被拒绝。该组检查覆盖宿主文件复制，手机 Files 界面操作、解码与出答各有独立的验收范围。

在提交 `5158cf3` 的实现中，这五个超限文件每个都触发了 512 次成功写块回调，每块 64 KiB。现在从已打开的源文件读取大小，在创建副本前拒绝已知超限文件。相同 42 个输入重放后，37 个仍成功，5 个仍超限，每个超限文件的写块数均降为零。源文件在复制期间增长时，逐块检查也会拒绝它，并清理已写入的数据。iOS 27.2 模拟器上的 13 项文件存储测试与 14 项宿主测试均通过。[超限与复制中增长的回归用例](../../probes/ios-multimodal-bridge/MultimodalInputStoreTests.swift)
